# Research notes: formats, classic techniques, timing

Condensed findings (web-verified 2026-07-28) that shaped the design.
Licensing research is separate in LICENSING.md.

## Atlas metadata formats

- **Aseprite JSON** (generated by `doc_exporter.cpp`,
  https://github.com/aseprite/aseprite/blob/main/src/app/doc_exporter.cpp;
  CLI: https://www.aseprite.org/docs/cli/): `frames` is a hash
  (default) or array (`--format json-array`); per frame `frame
  {x,y,w,h}`, `rotated` (always false — Aseprite never rotates),
  `trimmed`, `spriteSourceSize` (trim offset in canvas space),
  `sourceSize`, `duration` in ms. `meta` adds `frameTags`
  (`name/from/to/direction` with `forward|reverse|pingpong|
  pingpong_reverse`, optional string `repeat`), `layers`, `slices`
  (keys → `bounds` in canvas coordinates, optional pixel `pivot`).
  `meta.scale` is a string. The converter's Aseprite mode consumes
  exactly this; slices double as crop + anchor.
- **TexturePacker generic JSON**
  (https://www.codeandweb.com/texturepacker/documentation/custom-exporter):
  same frame-record shape (Aseprite cloned it), plus normalised
  `pivot`; `rotated:true` means 90° and w/h swap — the converter
  requires rotation off rather than guessing exporter direction.
- **libGDX/Spine `.atlas`** (https://esotericsoftware.com/spine-atlas-format):
  line-based text, `rotate: true` = 90° **counter**-clockwise —
  deliberately not shared with the JSON path; easy ~50-LOC addition.
- **`.aseprite` binary** is fully documented
  (https://github.com/aseprite/aseprite/blob/main/docs/ase-file-specs.md):
  little-endian, 128-byte header (magic 0xA5E0), frames with chunk
  lists; cel chunks type 2 hold zlib (RFC1950) pixel data; tags chunk
  0x2018 (direction byte, repeat word), palette 0x2019, slices
  0x2022. Direct parsing needs only Python `struct` + `zlib`; skipped
  for v1 because multi-layer blend-mode compositing is the hard part
  and the JSON export already flattens it.

## Classic talking-face architecture (why base + patches)

- **Sierra SCI portraits** (KQ6/GK1): a portrait is a base bitmap
  plus N mouth/expression bitmaps selected by timed sync data — binary
  "Sync" resources or ASCII "RAVE" (`tick count, lipSyncID, ...`)
  in the Windows KQ6 version. ScummVM's player draws base then the
  indexed overlay (`engines/sci/graphics/portrait.cpp`,
  https://raw.githubusercontent.com/scummvm/scummvm/master/engines/sci/graphics/portrait.cpp).
  FSPR's bank/slot model is this, generalised.
- **LucasArts**: baseline talkie practice was looping the talk
  animation for the audio duration; audio-driven sync came later
  (Aric Wilmunder interview,
  https://mixnmojo.com/features/sitefeatures/LucasArts-First-Words/1).
  Engine-level lip sync exists only for SCUMM v6+
  (https://wiki.scummvm.org/index.php?title=SCUMM%2FGame_Enhancements).
- **AGS** codified the 10-frame talking view: text-based letter→frame
  mapping or voice sync via Pamela/Papagayo/Rhubarb files
  (https://adventuregamestudio.github.io/ags-manual/v3/Lipsync.html);
  TotalLipSync's Rhubarb mapping is frame 0=X, 1=A … 9=H
  (https://github.com/messengerbag/TotalLipSync) — FSPR's shape enum
  matches that order (minus the Moho gap).

## Mouth shapes and timing constants

- **Rhubarb shape definitions** (verbatim source of the nine-shape
  canon): https://github.com/DanielSWolf/rhubarb-lip-sync README —
  A closed/pressed (M B P), B clenched teeth, C open (also the
  A/B→D in-between), D wide open, E rounded (also the C/D→F
  in-between), F puckered, G teeth-on-lip, H tongue raised, X idle.
  The engine's `transition_via` implements exactly those in-between
  rules.
- **Rhubarb timing** (rhubarb/src/animation/): `minShapeDuration` =
  70 ms, min open/closed segment 80 ms (timingOptimization.cpp);
  pauses < 120 ms hold the last shape, 120–350 ms relax, > 350 ms
  close (pauseAnimation.cpp). FSPR defaults: 70 ms hold, 120 ms
  close delay.
- **Animate on twos**: 2 frames at 30 fps = 66 ms ≈ Rhubarb's
  minimum — mouth changes at ~15 Hz read as natural limited
  animation (https://animationclub.school/blog/what-is-fps-or-frames-per-second/).
- **Blinks**: interval 2–10 s, duration ~100–400 ms
  (https://en.wikipedia.org/wiki/Blinking); animator recipe ≈ 8
  frames at 24 fps with ~2 closed and eased ends, blink on gaze
  changes (https://animationapprentice.blogspot.com/2018/03/why-animators-need-to-blink.html).
  FSPR: 80/40/120 ms envelope, 4 s hashed windows, occasional double
  blink, and a fraction of saccade epochs open with a blink.

## Storage techniques

- **RLE on real console tile data**: PackBits ≈ 12% saving on
  SMB+Kirby 2bpp tiles, pixel-oriented codecs up to 41%
  (https://www.nesdev.org/wiki/Tile_compression) — planar tiles are
  RLE-hostile. Flat indexed pixel art does far better: our four
  sheets compress to 18–53% of raw indices with plain PackBits
  (`generated/*.stats.json`).
- **Delta frames / dirty rectangles**: Autodesk FLIC stored
  frame-to-frame deltas (https://en.wikipedia.org/wiki/FLIC_(file_format));
  Abrash's dirty-rectangle chapter is the canonical write-up
  (https://www.phatcode.net/res/224/files/html/ch45/45-02.html).
  FSPR cells *are* delta patches spatially; temporal dirty-rect flush
  is left to the LCD layer.
- **Tile dedup** (NES nametables,
  https://www.nesdev.org/wiki/PPU_nametables): FSPR dedups whole
  cells by content hash; grid-of-8×8 dedup was measured as not worth
  the indirection at these cell counts.
- **Transparent index 0** is the GB/NES convention
  (https://gbdev.io/pandocs/Palettes.html) and costs nothing at ≤256
  colours — no separate mask plane.
- **Palette cycling** (Mark Ferrari,
  https://www.effectgames.com/effect/article-Q_A_with_Mark_J_Ferrari.html):
  animation with zero extra frame storage; FSPR's `sprite_cycle_t`
  rotates palette ranges on the sample clock (candle flame, status
  strip, phosphor shimmer in the demos).

## Keyframe→shape classification

`face_keyframe_t` carries continuous articulation (open/width/round/
press/teeth), not visemes, so the atlas holds `sprite_selector_t`
thresholds classifying into the nine shapes; defaults were tuned to
mirror the firmware's procedural `mouth_sprite_index` decision tree so
both renderer families read the same stream consistently. Viseme
debounce mirrors industry practice (Rhubarb's minima; cherry-lip-sync
ships an explicit single-frame-viseme filter,
https://github.com/amberwhitehead/cherry-lip-sync).
